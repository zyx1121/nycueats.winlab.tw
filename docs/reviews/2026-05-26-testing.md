## Critical（關鍵路徑沒測 / CI 漏）

- **`addToOrder` 零測試** — 整個系統 demand 最高的入口（下單 + 觸發 daily_slots CHECK constraint），逐字無對應 test [SOURCE: app/menu/[id]/actions.ts:8-78 vs no test file]。error.code `"23514"` → "此日期已售完" 這條分支是 slot-limiting 機制最後的防線，prod 出包就是 oversell，必須補 mock-based 測試（至少：未登入、新單成功、複用 pending order、CHECK constraint 23514、其他 DB error）。

- **CI 不跑任何測試** — `ci.yml` 只 lint + build [SOURCE: .github/workflows/ci.yml:19-23]，README 寫的「CI currently runs lint + build + e2e test」是錯的 [SOURCE: README.md:106]。後果：所有現存的 32 個 test case [SOURCE: grep "it\|test(" count = 32] 都不在 PR-gate 上，main branch 是否綠完全靠人工跑。最小修補：CI 加一個 `bun run test:unit` step（不需要 Supabase secrets，純 mock）；e2e 另開 workflow 用 service account credential。

- **`pickUpOrderItem` 零測試** — 這條動 `picked_up=true` + auto-complete order，且涉及跨商家權限驗證（`menu_items.vendor_id !== vendor.id` 才能擋）[SOURCE: app/vendor/orders/actions.ts:18-32]。商家 A 拿不到商家 B 的訂單這條 boundary 沒測 → demo 時就是事故。

- **`requireRole` 零測試** — auth guard 的單一進入點 [SOURCE: lib/auth.ts:5-19]，所有 vendor / admin actions 都套這條。沒測 = role array 包含關係（`["vendor", "admin"]` 對 `requireRole("admin")` 該過）這類邊界未驗。

## Important（mock 策略 / 補測建議）

- **Mock 過於 schematic，可能漏掉真 query bug** — `createQuery` 的 `eq` 用 `eqCallIndex` 數呼叫次數決定回什麼 [SOURCE: app/cart/actions.test.ts:24-40]，這只驗到 chain shape 對不對，驗不到 select 字串裡 `orders!inner(user_id)` join 拼錯之類的問題。這呼應 user 全域 CLAUDE.md「mock DB pass 但 prod migration fail」的提醒。建議升級：每組關鍵 server action 至少配一個 Supabase local container integration test（`bunx supabase start` 啟 local stack，跑真 query），跟現有的 mock 並行，不取代。

- **`recommendation.ts` 三函式零測** — `getTrendingItems` / `getNutritionPicks` / `getRandomPicks` 都有非平凡邏輯（trending 的 Map aggregation + topId order preservation [SOURCE: lib/recommendation.ts:27-72]、random 的 shuffle + exclude ordered ids [SOURCE: lib/recommendation.ts:117-146]），但連 pure-function-able 的部分（Map 累加、topId 排序）都沒拆出來測。建議把這幾個函式內的純邏輯抽到 `recommendation-model.ts`（如 `aggregateTrending(rows): TopId[]`），仿 `revenue-model.ts` 走純函式測試路線 [SOURCE: app/vendor/revenue/revenue-model.test.ts:90-128 demo this pattern]。

- **E2E 沒測 sold-out path** — `e2e/order-flow.spec.ts` 永遠選 `:not(:has-text('本週已售完'))` [SOURCE: e2e/order-flow.spec.ts:14]，等於只測 happy path。slot 滿 → race condition → CHECK 違反這條 critical path 在 e2e 看不到（也很難穩定 reproduce，所以更需要 unit-level 補）。

- **RLS boundary 完全沒測** — 學期報告通常會問「user A 看不到 user B 的訂單嗎」這種題。現有 mock test 都假設 user 已登入且查得到自己 row [SOURCE: app/cart/actions.test.ts:91-106]，沒有「RLS 把 row 擋掉 → query 回空陣列 → action 怎麼處理」的 case。RLS 屬 security agent 範圍，但「RLS 擋掉時 UX 行為對不對」是 testing 範圍。

- **E2E `serial` mode + 共用單一 storageState 容易 flaky** — `test.describe.configure({ mode: "serial" })` [SOURCE: e2e/order-flow.spec.ts:35] + `storageState: "e2e/.auth/user.json"` [SOURCE: playwright.config.ts:14] + `workers: process.env.CI ? 1 : undefined` [SOURCE: playwright.config.ts:9]：CI 上 serial 順跑 OK，但本地 default `undefined` workers 可能多 worker 共用同個 session storageState，會有 cart state contention（一個 worker 清空，另一個還在加）。建議：本地也強制 `workers: 1`，或每個 spec 跑前先呼叫 cleanup action 清 cart。
