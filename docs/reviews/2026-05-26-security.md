# Security Review — 2026-05-26

## Summary
RLS coverage 完整、所有 server actions 都過 auth/role 檢查、無 `service_role` 洩漏到 client。但有兩個 **可直接拿來提權 / 偽造金額** 的漏洞，加上一組過寬的 storage policy 使任何登入者能改別人的圖。整體 posture 中等偏弱，主要問題是「policy 寫了但 WITH CHECK 漏」這類細節型 RLS 缺口，必須在 prod 前收。

## Critical（漏洞 / 權限繞過 / PII 外洩）

- **任何 user 可自我升權為 admin / vendor** — `profiles_update_own` 只有 `USING (id = auth.uid())`，沒有 `WITH CHECK` `[SOURCE: supabase pg_policies, profiles_update_own qual="(id = auth.uid())", with_check=null]`。Server action `updateProfile` `[SOURCE: app/profile/actions.ts:13-30]` 只更 name/area_id 沒問題，但 RLS 在 PostgREST / 直連時不擋 user 從 client 直接 PATCH `role: ['admin']`。`profiles.role` default 是 `['user']` 但無欄位級限制 `[SOURCE: information_schema, profiles.role default=ARRAY['user'::text]]`。
  - 修法：加 `WITH CHECK (id = auth.uid() AND role IS NOT DISTINCT FROM (SELECT role FROM profiles WHERE id = auth.uid()))`，或更乾淨：把 `role` 欄位的 UPDATE 權限 revoke 給 `authenticated`（`REVOKE UPDATE (role) ON profiles FROM authenticated;`），只留 `profiles_update_admin` 能改 role。

- **下單可任意捏造價格** — `addToOrder` 接 client 傳來的 `basePrice` 與 `selectedOptions[].price_delta`，直接寫進 `order_items.unit_price` `[SOURCE: app/menu/[id]/actions.ts:13-72]`。Caller 從 `add-to-order-dialog.tsx` 帶 `item.price` `[SOURCE: app/menu/[id]/add-to-order-dialog.tsx:104]`，但 server action 端不重查 DB，攻擊者可在 server action call 帶 `basePrice=0` / 任意 `price_delta` 拿免費餐點，且報表會被汙染。
  - 修法：server 端 re-fetch `menu_items.price` by `menuItemId` + re-fetch `item_options.price_delta` by `option_id IN (...)`，只用 DB 真值算 `unitPrice`。Client 傳的 price 全部丟掉。同樣 pattern 用在 `vendor/menu` 的 upsertMenuItem 沒問題（因為那是 vendor 自己改自己菜單），但 user 下單路徑必須 server-side compute。

- **任何登入者可覆寫 / 刪除任意人的 vendor / menu 圖** — storage `vendor_images_auth_write/update/delete` 與 `menu_item_images_auth_*` policy 的 qual 只檢查 `bucket_id`，**沒檢查 owner / vendor 對應** `[SOURCE: pg_policies storage.objects, vendor_images_auth_write with_check="(bucket_id = 'vendor-images'::text)"]`。任何 authenticated user 都能對任一 path upload / overwrite / delete。`image-upload.tsx` 用 `upsert: true` 加 `Date.now()` 檔名 `[SOURCE: components/image-upload.tsx:41,45]`，攻擊者只要 brute-force path（或從 DB 讀 image_url）就能換掉別人商家的封面。
  - 修法：把 storage policy 改成檢查路徑前綴 owner，例如 `(storage.foldername(name))[1] = auth.uid()::text`，並把 client upload 路徑改成 `${user.id}/...`；或更直接：把 image upload 改成走 server action（passthrough 給 storage 用 server-side check 過的 vendor.id）。

## Important（容易踩雷 / 需要硬化）

- **`vendors_read_active` policy 對 anon 也開放** — qual=`(is_active = true)` 沒有 `auth.uid() IS NOT NULL` 限制 `[SOURCE: pg_policies, vendors_read_active qual="(is_active = true)"]`。雖然 `proxy.ts:35-38` 對非 public path 一律 redirect 到 /login，但 PostgREST 端點不過 proxy，anon key 可以直接 `GET /rest/v1/vendors?is_active=eq.true` 拉到完整 vendor 名單（含 owner_id、description、image_url）。同樣問題：`menu_items_read`、`item_option_groups_read`、`item_options_read`、`daily_slots_read`、`areas_read`、`vendor_areas_read` 都是 `qual = true`。
  - 修法：如果不需要對未登入者開放（員工內部站，看起來不需要），改成 `(SELECT auth.role()) = 'authenticated' AND is_active = true`。policy 寫對之後可以省掉一個攻擊面。

- **`addToOrder` 不驗 `dailySlotId` 是否屬於指定的 `menuItemId`** — client 帶兩個獨立 id，server 沒交叉檢查 `[SOURCE: app/menu/[id]/actions.ts:46-58]`。攻擊者可拿 A 商品的 slot 配 B 商品的 menuItemId 下單，trigger 更新到錯的 slot 的 `reserved_qty`，繞過 oversell 防護。
  - 修法：insert 前先 `select from daily_slots where id = dailySlotId and menu_item_id = menuItemId`，不符就 reject。

- **`addToOrder` 對 `qty` / `price_delta` / `selectedOptions` 無上下界 / type guard** — 沒 zod 沒手寫 check，`qty` 可帶負數、`selectedOptions` 可帶不屬於該菜單的 option_id `[SOURCE: app/menu/[id]/actions.ts:8-72]`。trigger `update_reserved_qty` 對負 qty 會減 `reserved_qty` 反而開放更多名額。
  - 修法：server action 開頭加 zod schema：`qty >= 1 && qty <= max_qty`、`selectedOptions[].option_id IN <該 menu_item 的合法 options>`。同樣套用到 `bulkUpsertSlots`、`upsertMenuItem` 等所有收 user input 的 Server Action。

- **`profiles` 沒 INSERT policy** — `handle_new_user` trigger 是 SECURITY DEFINER 自動建 profile `[SOURCE: pg_proc handle_new_user]`，但若 trigger 失敗 / 漏觸發，沒 fallback。更重要：trigger 直接從 `raw_user_meta_data->>'full_name'` 與 `avatar_url` 寫入 `[SOURCE: handle_new_user definition]`，這些欄位 OAuth 回傳但 user 可控（透過編輯 Google 帳號）→ XSS 入庫風險（雖然目前都當 text render，但若未來 dangerouslySetInnerHTML 就破）。
  - 修法：對 name/avatar_url 在 trigger 內做長度截斷 + URL scheme allowlist（avatar_url 只接受 `https://`）。

- **error.tsx / global-error.tsx 沒輸出 stack 是好的，但 Server Action 的 error 直接 `return { error: error.message }`** — 例如 `updateProfile` `[SOURCE: app/profile/actions.ts:26]`、`updateVendorInfo` `[SOURCE: app/vendor/profile/actions.ts:22]`、`upsertMenuItem` `[SOURCE: app/vendor/menu/actions.ts:46]` 等多處。Supabase error.message 可能含 column 名 / constraint 名 / SQL detail，洩漏 schema。
  - 修法：包一個 `mapDbError(err)`，內部 console.error 真錯，對外只回 generic message（已經有部分 actions 這樣做如 `confirmOrder` 回「確認失敗」）。

## Nit（不緊急但建議）

- `lib/auth.ts` 的 `requireRole` 在失敗時 `throw new Error("權限不足")` `[SOURCE: lib/auth.ts:16]`，會被 Next.js error boundary 接住但 message "權限不足" 對 user 算 OK；只是 console / log 端會 stack trace。建議升級到 `redirect('/')` 統一 layout 的行為，避免 UX 雙標。

- `proxy.ts` 用 `pathname.startsWith(p)` 比對 publicPaths `[SOURCE: proxy.ts:36]`。`/login` 開頭涵蓋 `/login/anything`，目前不會出事（沒 `/login/*` 子路由）但設計上不嚴謹，建議改 exact match 或加上 trailing `/` 判斷。

- Auth leaked password protection 未開（Supabase advisor warn `[SOURCE: get_advisors security, auth_leaked_password_protection]`），但專案只開 Google OAuth（看 `signInWithEmail` 還是有 `[SOURCE: app/login/actions.ts:8-28]`），如有員工會用 email/password 走道，建議在 Supabase Dashboard 打開。

## What's good（已經做對的部分）

- 所有 11 張 public table RLS 都 enabled `[SOURCE: pg_class rls_enabled query, 全 true]`
- 所有 admin / vendor server actions 都過 `requireRole` `[SOURCE: app/admin/**/actions.ts, app/vendor/**/actions.ts]`，無 silent bypass
- 所有 SECURITY DEFINER function 都 `SET search_path TO 'public'` 防 search_path attack `[SOURCE: pg_proc handle_new_user/is_admin/is_vendor_order/update_reserved_qty 全有 SET search_path]`
- Supabase client 全用 `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_DEFAULT_KEY`（anon key），無 `SUPABASE_SERVICE_ROLE_KEY` 在 codebase 任何角落 `[SOURCE: grep -rn "service_role" 整 repo 無結果]`
- `auth/callback/route.ts:8` 對 `next` 參數做了 `startsWith("/") && !startsWith("//")` 防 open redirect — 寫得很對 `[SOURCE: app/auth/callback/route.ts:8]`
- `cart/actions.ts` 所有 mutate 都先驗 `order.user_id == user.id` + `order.status == 'pending'` 才執行 `[SOURCE: app/cart/actions.ts:11-94]`
- `pickup/route.ts` 三段驗證：vendor role → vendor 擁有 → order_item 屬於該 vendor → status confirmed → 才標 picked_up `[SOURCE: app/api/pickup/route.ts:14-51]`
- `vendor/menu/actions.ts` 用 `requireMenuItemOwnership` helper 確保每個 menu/option mutate 都檢查 `vendor_id` 對應 `[SOURCE: app/vendor/menu/actions.ts:18-26]`
- Server Action 本身 Next.js 預設帶 origin check，CSRF 默認過關（cookie SameSite=Lax 也是 Supabase SSR helper 預設）
